# Нативное падение при переключении окон — 2026-11-03

## Воспроизведение вне мода

`tools/kt/GlfwFocusProbe.java` создаёт одно окно GLFW с `GLFW_CLIENT_API=GLFW_NO_API`.
Minecraft, NeoForge, Thaumcraft, JEI и OpenGL не загружаются. Использованы локальные jar LWJGL 3.3.3
из Gradle; `glfwGetVersionString()` сообщает `3.4.0 Win32 WGL Null EGL OSMesa VisualC DLL`.
Два отдельных процесса java/javaw создали окна A и B. Активация A прошла; прямая активация B
через Windows-инструмент завершилась `failed to activate captured window`, B упал в
`glfw.dll+0x101ab`. Это тот же адрес внутри DLL, что во всех трёх падениях Minecraft.
Отчёт: `build/kt-evidence/glfw-without-minecraft-crash.log`.

Это доказывает, что код Thaumcraft и графический контекст OpenGL не являются необходимыми условиями сбоя.
Утверждать, что никакой другой краш в моде невозможен, по этому результату нельзя.

## Место сбоя и рабочая гипотеза

Инструкция в hs_err читает байт по `window + key + 0x90`; регистр key равен 340 — левый Shift.
Предшествующие инструкции соответствуют получению активного окна, его свойства GLFW и проверке четырёх
клавиш-модификаторов в обработчике событий Win32. В [исходниках GLFW](https://github.com/glfw/glfw/blob/3.4/src/win32_window.c)
этот участок получает `window` из `GetPropW(GetActiveWindow(), L"GLFW")` без проверки принадлежности процесса.

По [документации Windows](https://learn.microsoft.com/windows/win32/procthread/creating-windows-in-threads),
потоки с общей очередью ввода разделяют понятие активного окна. Поэтому вероятное объяснение —
во время принудительной активации GLFW получает HWND другого процесса, затем пытается прочитать его
GLFWwindow как собственную память. Внутренняя реализация инструмента Windows не исследовалась;
конкретный вызов AttachThreadInput не трассировался, поэтому эта часть остаётся гипотезой.

## Обход для приёмки

Первоначальное Swing-окно не имело свойства GLFW, но делило javaw.exe с одним из клиентов.
После возобновления получено ещё одно падение (`build/kt-evidence/client1-native-crash-resume.log`);
первый обход нельзя считать полностью надёжным. Дополнительно обнаружен скрытый запуск второго клиента.
Он изменён на видимый режим для запрошенной пользователем интерактивной проверки.

Собственное WinForms-окно `tools/kt/FocusBridge.cs` имеет отдельный `KtFocusBridge.exe` и не использует GLFW.
Переключение выполняется **GLFW A → нейтральное окно → GLFW B**. На минимальном стенде исходный Swing-вариант
B2 → bridge → A → bridge → B2 прошёл, оба heartbeat продолжили расти, нового hs_err не было.
После позднего повторения сбоя для Minecraft используется отдельный WinForms exe.
Для каждого перехода используется штатный computer-use, без Win32-инъекций или изменения системных настроек.
Обход не заменяет GLFW и не меняет итоговый jar Thaumcraft. С отдельным нейтральным exe и видимым
вторым клиентом переходы прошли; проверены печати с обоих ракурсов, настройка владельцем и членом команды,
отклонение чужого изменения. Длительная надёжность обхода ещё проверяется.

Нельзя напрямую активировать фоновый Minecraft, пока активен другой Minecraft/GLFW. Сначала активировать
собственное нейтральное окно, получить его состояние, затем активировать нужный клиент и получить состояние.
При работе в одном активном клиенте дополнительные переключения не нужны.

Пользователь отдельно разрешил продолжать разбор после трёх попыток; старый предел для этой задачи снят.
