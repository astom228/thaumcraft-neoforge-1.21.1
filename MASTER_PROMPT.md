# MASTER_PROMPT — порт Thaumcraft 6 (1.12.2) на NeoForge 1.21.1

Ты работаешь над моим личным проектом: порт мода Thaumcraft 6.1.BETA17 (Minecraft 1.12.2, Forge)
на Minecraft 1.21.1 (NeoForge). Только для личного использования, без публикации.
Этот файл — главная инструкция. Читай его в начале каждой сессии вместе с CLAUDE.md,
PORTING_PLAN.md и PROGRESS.md.

## 0. РЕЖИМ РАБОТЫ

### 0.1 Автономность
- Работай самостоятельно, этап за этапом, без моего подтверждения на каждое действие.
- Останавливайся и жди меня ТОЛЬКО в трёх случаях:
  1. Контрольная точка (см. раздел 3) — нужна моя проверка в игре.
  2. Решение, которое меняет игровой процесс или отступает от оригинала, и которого нет в этом файле.
  3. Ты застрял: одна и та же ошибка не исправляется после 3 разных попыток.
- В остальных случаях принимай разумное решение сам и записывай его в DECISIONS.md.

### 0.2 Файл прогресса PROGRESS.md (обязательно)
Создай его в корне и обновляй после каждого законченного подшага:
- текущий этап и подшаг;
- что сделано (кратко);
- что осталось в текущем этапе;
- известные проблемы и TODO;
- последний коммит.
Если сессия прервётся (лимит, закрытие VS Code), по фразе «продолжай» ты должен
прочитать PROGRESS.md и продолжить ровно с того места.

### 0.3 Git
- Коммит после каждого законченного подшага, если gradlew build проходит.
- Сообщения коммитов на русском: «Этап N: что сделано».
- Никогда не коммить reference/, build/, run/, .gradle/.
- Если что-то сломал и не можешь быстро починить — откатись к последнему рабочему коммиту
  (git restore / git reset --hard к последнему коммиту этапа) и попробуй иначе.
- Никаких git push и remote — репозиторий только локальный.

### 0.4 Проверки после каждого подшага
1. `gradlew build` — должен пройти без ошибок.
2. После этапов, где добавляются регистрации (блоки, предметы, сущности, биомы и т.д.):
   запусти выделенный сервер (`gradlew runServer`, при первом запуске создай run/eula.txt с eula=true
   и включи в server.properties online-mode=false), дождись строки "Done" в логе, затем останови.
   Это ловит падения на регистрации без моего участия. Логи смотри в run/logs/latest.log.
3. Если доступно — `gradlew runData` для генерации моделей/рецептов/тегов, проверь, что прошло без ошибок.
4. `gradlew runClient` сам НЕ запускай — клиент проверяю я на контрольных точках.

### 0.5 Экономия контекста и лимитов
- Не читай весь декомпилированный код целиком. Ищи нужные классы через grep/поиск по reference/src-mcp.
- Работай подшагами по 5–15 файлов, не пытайся перенести этап одним махом.
- Не выводи в чат длинные листинги кода — просто создавай/правь файлы.
- Отчёты в чат — короткие.

## 2. ПРАВИЛА ПЕРЕНОСА

### 2.1 Верность оригиналу
- Механика, числа, рецепты, стоимость в аспектах, прочность, урон, шансы, время — 1:1
  по коду оригинала. Ничего не «улучшать», не балансировать, не придумывать.
- Если перенести 1:1 невозможно из-за ограничений 1.21.1 — сделай максимально близко
  и запиши в DEVIATIONS.md: что было, что стало, почему.
- Текстуры, звуки, модели — из оригинала, без изменений содержимого.
  Разрешено только: переименование, перенос в новые папки, конвертация формата JSON-моделей.

### 2.2 Техническая база NeoForge 1.21.1
Используй современные подходы, не тащи старые:
- Регистрация: `DeferredRegister` / `DeferredHolder` / `DeferredBlock` / `DeferredItem`.
- Данные предметов: Data Components (вместо NBT в ItemStack). Свои компоненты регистрируй
  через `DataComponentType` с Codec и StreamCodec.
- Данные игрока/чанков/мира: Data Attachments (вместо capabilities из 1.12),
  сохранение через Codec, синхронизация пакетами.
- Сеть: `CustomPacketPayload` + `RegisterPayloadHandlersEvent`, с чётким разделением
  клиент/сервер.
- Рендер: `PoseStack`, `VertexConsumer`, `RenderType`, `MultiBufferSource`.
  Прямой GL11 / Tessellator из 1.12 не использовать. Свои RenderType — при необходимости.
- Частицы: `ParticleType` + `ParticleProvider`, регистрация в событиях клиента.
- Блоки с логикой: `BlockEntity` + `BlockEntityType`, рендер через `BlockEntityRenderer`.
- GUI: `AbstractContainerMenu` + `AbstractContainerScreen`, регистрация `MenuType`.
- Рецепты: свои `RecipeType` и `RecipeSerializer` с Codec; сами рецепты — JSON в data/,
  генерировать через datagen там, где удобно.
- Модели, blockstates, теги, loot tables, рецепты: предпочтительно datagen
  (`GatherDataEvent`), иначе — аккуратные JSON вручную.
- Мировая генерация: data-driven (configured/placed features, biome modifiers),
  биомы — через TerraBlender.
- Всё, что в оригинале считалось в отдельном потоке (аура), переносить на серверный тик
  с распределением нагрузки по тикам, без своих потоков.
- Строгое разделение клиентского кода: клиентские классы только в отдельном пакете
  `client`, регистрация через `@EventBusSubscriber(value = Dist.CLIENT)`.

### 2.3 Аспекты и рецепты
- Аспекты предметов в оригинале частично вычисляются из рецептов. В 1.21.1 рецепты есть
  только на сервере → вычислять на сервере после загрузки рецептов и синхронизировать
  клиенту пакетом при входе и при /reload.
- Явные назначения аспектов из оригинала перенести как данные (JSON в data/thaumcraft/
  или код-регистр — выбери удобное и зафиксируй в DECISIONS.md).

### 2.4 Русский язык (обязательно)
- `en_us.lang` и `ru_ru.lang` из оригинала конвертировать в `en_us.json` и `ru_ru.json`
  (лучше скриптом), ключи переименовать под формат 1.21
  (`item.X.name` → `item.thaumcraft.X` и т.п.), значения не менять.
- Устаревшие ключи, которые не используются, не переносить.
- Непереведённые и отсутствующие строки — переводить на русский, сверяясь с GLOSSARY_RU.md,
  пополняя его новыми терминами.
- Разметку книги, коды `§`, `%s`, переносы строк — сохранять как есть.
- Каждая новая строка сразу добавляется в оба файла.
- Переводить строки того, что переносится на текущем этапе. Тексты исследований —
  начиная с этапа 7, по разделам книги.
- Качество: живой русский, стиль и атмосфера оригинала, не дословный машинный перевод.
